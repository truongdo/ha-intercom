# Host-Initiated Proactive Call Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Home Assistant hits a new `GET /api/call/trigger?token=...` endpoint; the host notifies the configured Telegram group; whoever opens the app and taps the button connects immediately, skipping the ring/confirm flow even if `pickup_mode` is `"confirm"`.

**Architecture:** A new in-memory, time-limited "next call skips confirmation" flag on `SessionManager`, armed by a new `trigger_bypass()` method and consumed once by whichever call connects next. A new HTTP route reuses `call_confirm_token` auth (same pattern as confirm/reject) and the existing `telegram.send_message`. No frontend changes.

**Tech Stack:** Same as sub-projects 1 and 2 — Python 3.11+/Starlette, stdlib only.

**Spec:** [`docs/superpowers/specs/2026-09-22-host-call-design.md`](../specs/2026-09-22-host-call-design.md)

## Global Constraints

- The trigger endpoint reuses `call_confirm_token` — no separate token (spec: "Trigger endpoint auth").
- The bypass is an in-memory flag on `SessionManager`, never a temporary change to the persisted `pickup_mode` setting (spec: "Skipping confirmation for the resulting call").
- The bypass window is a hardcoded 5 minutes (`300.0` seconds) — not a new `config.toml` knob (spec: "Bypass window").
- `public_url` is optional; the feature works with or without it (spec: "Telegram message link").
- No frontend changes in this sub-project (spec: "Frontend changes").
- `trigger_bypass()` always succeeds regardless of whether the Telegram send succeeds — it's armed before the Telegram call is attempted, not after (spec: "Error handling").

### Task 2: `trigger_bypass()` on `SessionManager`

**Files:**
- Modify: `backend/live_intercom/session.py`
- Modify: `backend/tests/test_session.py`

**Interfaces:**
- Consumes: nothing from Task 1 (this task is independent of it).
- Produces: `SessionManager.trigger_bypass() -> None`. `SessionManager.__init__` gains an **optional** `clock: Callable[[], float] = time.monotonic` parameter — since it has a default, `web.py`'s existing `SessionManager(...)` call site does *not* need to change for this task, unlike sub-project 2's `pickup_mode_provider`/`ring_timeout_s` (which had no defaults and forced a same-task change). Task 3 calls `manager.trigger_bypass()` from the new HTTP route; it needs no other new interface from this task.

**Why no lock is needed here** (unlike `confirm()`/`reject()`'s `_resolve_lock` from sub-project 2): `trigger_bypass()` is a single, unconditional attribute write (`self._bypass_until = ...`), not a check-then-claim sequence — calling it twice in a row is harmless (it just resets the window). `_consume_bypass()` is only ever called from `_run()`, which never runs concurrently with itself (the existing `_active` flag already guarantees only one session at a time). The one cross-thread interaction — a `trigger_bypass()` call from an HTTP handler racing a `_consume_bypass()` read on the session's event loop — reads/writes a single attribute, which CPython's GIL already makes atomic (no torn reads), and either outcome (the connecting call catches the brand-new trigger or narrowly misses it) is an acceptable, already-accepted raciness in this design — not a correctness bug to guard against.

Add the two new methods, right after the `reject`/`_resolve` methods and before `handle`:

```python
    def trigger_bypass(self) -> None:
        self._bypass_until = self._clock() + BYPASS_WINDOW_S

    def _consume_bypass(self) -> bool:
        armed = self._bypass_until is not None and self._clock() < self._bypass_until
        self._bypass_until = None
        return armed
```

- [ ] **Step 2: Add the route to `web.py`**

In `backend/live_intercom/web.py`, add this handler after `call_reject` and before `ws_endpoint`:

```python
    async def call_trigger(request: Request) -> Response:
        settings = await load_admin_settings()
        if isinstance(settings, Response):
            return settings
        supplied = request.query_params.get("token", "").encode()
        configured = settings.call_confirm_token.encode()
        if not configured or not hmac.compare_digest(supplied, configured):
            return JSONResponse({"error": "unauthorized"}, status_code=401)
        manager.trigger_bypass()
        if not settings.telegram_bot_token or not settings.telegram_chat_id:
            return JSONResponse({"ok": False, "reason": "not_configured"})
        text = (
            f"📞 Someone wants to talk — open the intercom to answer: {config.public_url}"
            if config.public_url
            else "📞 Someone wants to talk — open the intercom to answer."
        )
        ok, reason = await asyncio.to_thread(
            send_message, settings.telegram_bot_token, settings.telegram_chat_id, text
        )
        return JSONResponse({"ok": ok, "reason": reason})
```

Note `manager.trigger_bypass()` is called *before* the Telegram send is attempted — it always arms, regardless of whether the notification succeeds, matching the Global Constraints.

Add the route to the `routes` list, after `/api/call/reject`:
